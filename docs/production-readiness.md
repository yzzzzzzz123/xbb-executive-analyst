# 生产验收与运行手册

本项目采用 Windows 常驻 Codex App Server、按授权主体隔离的持久 Thread，以及唯一的销帮帮只读 runner。这里的“生产验收”是分层验证流程；离线测试通过只证明本地逻辑和异常路径满足测试合同，不能据此承诺企业微信端到端延迟、外部 API 可用性或持续在线率。

## 目录与依赖边界

| 目录 | 责任 | 允许的主要依赖 |
| --- | --- | --- |
| `skills/xbb-executive-analyst/` | 经营分析规则、字段和事实口径、唯一只读查询入口 | bundled runner 与确定性事实编译 |
| `skills/xbb-executive-chart/` | 经营图选型与规格合同；同轮辅助依赖 | 不取数、不独立回答经营问题 |
| `shared/security/` | 身份授权、公司范围、事实隐私与输出脱敏 | Node 标准库；不依赖业务或通道 |
| `shared/observability/` | 无正文的阶段计时与运行指标 | 标准库、安全基础设施；不反向依赖业务 |
| `shared/xbb/` | 查询网关、runner 隔离、聚合、模型事实视图、确定性绘图 | 安全层、可观测性、图表合同 |
| `shared/rag/` | 版本化规则索引与路由 | 本地规则文件、安全层、可观测性 |
| `shared/codex/` | App Server、Thread 生命周期、受控工具与上下文管理 | 安全、规则、业务网关和合同 |
| `shared/wecom/` | 消息协议、排重、发送、进程租约与连接恢复 | Codex 接口、安全层、消息格式化和绘图；启动时可恢复 runner 隔离 |
| `scripts/` | 部署、维护、离线验证与显式在线探针 | 通过受控运行入口执行 |
| `tests/` | 单元、组件集成、Windows 平台验收 | 仅使用测试构造数据、临时路径和替身 |

`tests/verify-project-boundaries.js` 扫描实际运行模块的 CommonJS 依赖并检查循环依赖，禁止安全/规则层启动网络或子进程，禁止企微层直接调用取数网关或事实编译器，禁止上层直接访问销帮帮凭据。新增共享目录、第三方依赖或跨层入口时应明确其责任并更新允许规则。该检查是架构约束；动态执行和数据授权仍由运行时验证保障。

## 一致的离线验收入口

依赖：Windows PowerShell 5.1、Node.js 22 或更高版本、Python 3 与 `PyYAML==6.0.2`。GitHub Actions 使用 Windows Server 2022、Node.js 22、Python 3.12 和相同锁定依赖，不要求本机 Codex 登录或真实业务凭据。

```powershell
npm ci
python -m pip install PyYAML==6.0.2
npm run verify:production
```

| 命令 | 范围与含义 |
| --- | --- |
| `npm run test:list` | 显示各组完整 suite 清单；启动即检查漏登记、重复与文件缺失 |
| `npm run test:unit` | 安全、规则、恢复、状态、排重、启动器及依赖边界等确定性模块测试 |
| `npm run test:integration` | 事实网关/跨月消费者、图表、App Server 与企微协议组件组合；使用替身及本地进程 |
| `npm run test:windows` | DPAPI 安全配置往返、计划任务/进程身份/隔离恢复的平台验收；不安装正式任务 |
| `npm test` | 以上三组全部执行，保留原有全部 suite；Windows 环境缺失会失败，不会静默跳过 |
| `npm run verify` | JavaScript/PowerShell 语法、两个 Skill 包的 YAML/正文合同和禁用运行时扫描；不重复运行测试 |
| `npm run verify:production` | `verify` 加全部测试，每个 suite 只执行一次 |
| `npm run bench:production` | 离线性能基准；测试输入与生产事实隔离，结果仅代表本机代码开销 |

分组保留现有测试文件，避免为了分类拆散已有跨模块断言。单元组允许本地临时文件，集成组可能执行受控子进程；分组不代表获得外网或正式凭据授权。所有新建 `tests/verify-*.js`、`tests/verify-*.ps1` 必须在 `scripts/run-tests.js` 登记，独立运行任何一组也会先核对全量清单。

完整验收中，JavaScript/PowerShell 语法错误、Skill 合同不合法、非法运行时、未登记测试、任一 suite 失败都会以非零状态退出。每个 suite 输出耗时，便于定位测试自身变慢；该耗时不等同于机器人响应耗时。

从 PowerShell 7 启动测试时，runner 仅对 Windows PowerShell 5.1 子进程清除继承的 `PSModulePath`，由 5.1 重建原生模块路径；其他环境变量与 Node 测试环境不变。这样避免错误加载 Core 版安全模块，但仍真实执行 DPAPI 往返和计划任务验收。

所有 PowerShell 源码必须是有效 UTF-8；包含中文等非 ASCII 内容的脚本必须带 UTF-8 BOM，保证英文 Windows PowerShell 5.1 不会按本地 ANSI 编码误读。`verify` 在语法解析前执行编码门禁，`.editorconfig` 为 `*.ps1` 固定 `utf-8-bom`。源码顺序断言必须先确认查找位置存在，不能让 `IndexOf` 返回的 `-1` 形成误通过。

## 真实只读低频探针

离线通过后，使用与后台机器人相同的 Windows 用户验证真实 App Server 登录、模型可用性和受控业务读取。在线探针串行、低频执行，一次选择最小必要范围；不得循环向业务 API 压测，也不得拿离线构造数据替代线上事实。

```powershell
npm run smoke:app-server
npm run smoke:business
npm run bench:production -- --live --repeat=3 --context
npm run bench:production -- --live --repeat=1 --business
```

先核查 `scripts/smoke-codex-app-server.js` 当前支持的参数与默认范围。通用探针验证模型链路，业务探针验证实时查询、事实校验和回答流程；二者不直接向企微联系人发送消息，不能单独证明企微图片上传、消息送达或手机显示正常。运行前确认没有重复探针和资源争用；运行后核查临时事实包已清理。若更改 runner 路径、聚合或事实口径，必须按 `AGENTS.md` 执行一次最小真实只读冒烟。

生产延迟分开记录首个状态、首段正文、取数排队、取数完成、模型完成、绘图及发送完成。离线图形/路由基准、真实模型探针和真实业务探针分别注明环境、样本数、范围、缓存状态、成功/失败结果。单次观测不能计算有代表性的 P95，也不能直接得出稳定性结论；持续服务指标只能从生产样本积累，不把超时或失败从统计口径中删除。

`bench:production` 默认仅进行离线故障注入；`--live` 才访问实际模型，`--business` 才允许一次当前月 performance 只读查询。通用场景显式拒绝业务工具。`--context` 使用标明虚构的数据库材料，并在隔离探针会话中触发一次 Thread 轮换，核对目标、30 秒窗口、90 天兼容及不删除旧字段；不会在数据库执行 SQL，也不修改正式会话。报告存放于 Git 忽略的 `test-results/production/`，只保留耗时、固定状态与验收布尔值，不保存答复正文和经营数字。失败样本也进入报告。

业务探针在开始前及调用网关前检查配置中的正式会话状态，但检查不是跨进程互斥锁；应由维护人协调低流量窗口，不能并行启动多个业务探针。结束时只有在 runner 标记安全清空后才删除探针目录；无法确认进程隔离时保留恢复证据并失败关闭。

### 交付时延与指标定义

经营结论生成后先在同一个回复流中展示完整可读正文，再制作和发送图片，最终包仍满足“图片或可信兜底图”的约束。图片上传内部已经有 SDK 分片重试，默认不再叠加整图重传；独立图片发送失败时改走回复内嵌图。进度发布器在结论就绪时关闭并丢弃待发送的旧阶段，避免结论被旧进度覆盖。

`request_measured` 每个新授权请求最多记录一次，使用独立随机 `requestTrace`，字段严格白名单：

| 指标 | 定义 |
| --- | --- |
| `firstReplyMs` | 首个状态包获得通道回执；不是模型首字 |
| `analysisMs` | 等待 Agent 的整体时间，含其内部会话等待、取数和生成 |
| `answerReadyMs` | 正文在应用内就绪的累计时间 |
| `answerVisibleMs` | 首个含完整正文的包获得通道回执；不是手机端已读 |
| `progressDrainMs` | 关闭旧进度发布器时的等待时间 |
| `queryQueueMs` / `queryRunMs` | 当前请求拥有的已结束查询订阅的排队/执行总时长；执行包含重试、校验和清理 |
| `renderMs` / `uploadMs` / `mediaDeliveryMs` | 绘制、整图上传等待和独立图发送等待的阶段时间 |
| `totalMs` | 本次处理成功结束或失败返回的累计时间 |

阶段可以重叠，不能把全部指标简单相加。`outcome` 区分 success、degraded、failed、unsupported；`imageDelivery` 区分 none、standalone、inline、failed。没有回执的阶段不虚构成功耗时；重复消息重放不再次计入新请求。实际取数调度另提供可选 `onTiming`，输出 queued/started/completed 等状态、queueWaitMs、runMs 和 shared，不输出查询条件或事实。

默认等待预算：旧进度 6 秒、单次回复 7 秒、单次渲染 10 秒、整图上传 15 秒、独立图发送 6 秒。这些是应用等待上限，不承诺能取消 SDK/Sharp 已发出的在途工作；上传迟到结果不能再触发新的媒体消息，退避跨过截止不能启动下一次重试。当前锁定 SDK 对同一 req_id 串行发送回复并提供 5 秒 ACK 截止，升级 SDK 必须重验该顺序约定。

## 复杂上下文与数据库调整任务

经营问题按期间、公司/人员和数据域建立确定性查询计划，跨月取数与聚合在本地完成，模型只接收预算内的管理事实视图。规则、当前事实和用户意图分开管理；范围修正必须撤销旧查询，不能复用旧范围事实。需要读取更大范围时，切分依据是业务边界和依赖关系，而不是按固定字符数截断后丢弃中间内容。

“调整一个数据库”属于通用工程任务，应先区分用户要求的是设计评审、SQL 方案还是实际执行。当前企微 Agent 的工具与沙箱保持只读，不能宣称已写入数据库，也不能借经营查询工具执行 DDL/DML。合理的工作分解为：

1. 固定目标与验收条件：数据库类型、目标行为、涉及表/服务、停机限制和兼容要求；未知项明确标记，不能猜测真实库结构。
2. 收集最小结构上下文：涉及的表定义、索引、约束、依赖查询及已脱敏的数据量分布；按表或业务模块读取，不上传整个库。
3. 建立依赖与迁移阶段：先扩展兼容结构，再进行有界回填和校验，再切换读写路径，最后在单独窗口移除旧结构；适用性取决于实际数据库。
4. 每个阶段保留可复核交付：SQL/迁移文件、预期影响、锁与事务边界、检查语句、失败停止点和回退条件。后续阶段只携带目标、已确认结构、已完成证据和未决项。
5. 在隔离测试环境执行与验证；正式写库由具备数据库执行权限的部署流程处理。机器人明确说明方案完成与实际执行之间的状态差异。

聊天输入若超过接收预算，必须明确提示分批提供上下文，不能静默截断用户要求后继续承诺完成。任务检查点描述目标、约束、当前范围、已验证结果和下一步，不输出模型内部思维过程或把旧经营数字当作新事实。

已实现的自动续接摘要只保存用户目标、关键约束与近期修正，不保存模型答复、代码材料或工具事实；最多 6 KiB，仅在进程内存中。长消息原文仍有 32 KiB 硬上限，按段落使用 4 KiB 软分组，完整 SQL/JSON/代码块不因软预算被切断。摘要不等于完整历史：省略项会明确标记，换 Thread 后需要精确表结构或 SQL 时必须重新核实材料。通用与经营路由之间不携带摘要，独立新问题不能继承旧数据库阶段模板，用户阈值/Top N 是筛选意图而非经营事实。

当前 Turn 绝对截止仍从活动回合建立开始；会话队列和取数队列各有独立容量/期限，尚未改为覆盖“消息接收 → 会话排队 → 全部交付”的统一 SLA 截止。不要把配置中的模型超时解释成端到端承诺。

## 空闲重载与回滚

部署前记录当前远程已推送的提交和工作区状态，保存离线验收结果。此次生产化优化前的 Git 基线为 `182253d`；它用于定位完整源码版本。任务 XML 备份只恢复计划任务定义，不回退同一路径下的代码。

1. 检查当前服务租约、活跃请求和 runner 隔离标记，等待没有正在执行的用户请求后进入维护窗口。确认当前部署路径及配置路径，保留仓库外的 DPAPI、访问策略、状态和日志。
2. 从同一 Windows 用户运行 `scripts/install-wecom-task.ps1` 的既有受控升级流程。该流程管理双任务、维护锁、进程身份和孤儿 runner；避免绕开维护器手动启动第二实例。
3. 核查新代际租约进入 `running`、企微重新认证、旧进程和 runner 无残留，再执行最小连通性核查。需要企微实际送达验证时，由授权的验收会话发起并检查文字/图片。
4. 若验收失败，保持受控维护状态，先保留失败日志摘要和当前未提交变更，再将代码恢复到审核过的 Git 基线；不得用破坏性重置覆盖未保存的用户变更。执行该版本匹配的依赖安装和任务安装流程，重复租约/认证/只读探针检查。

回滚必须同时考虑源码、锁文件和运行任务；不能只恢复任务 XML 就宣布代码回滚完成。机器关机、睡眠、注销或断网造成的离线属于部署环境限制，持续在线验收必须在实际运行主机进行。
